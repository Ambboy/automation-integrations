Первая реализация общей системы собственных расширений: отдельный сервис, постоянная очередь SQLite, модульный интерфейс и внешний мост Hermes. Python 3.11+, Linux; Python-зависимостей во время работы нет. Исходники Hermes не изменяются.

**Статус: изолированный кандидат v0.1, не включён в production.** Автоматические события с достоверным адресатом требуют контракта `request_origin`, которого нет в проверенной чистой базе Hermes `298df082` и в исследованных hooks официального `37dd129a` от 03.10.2026. Мост загружается на этой базе, но не отправляет события с угаданным маршрутом. Это ограничение функциональности, а не рекомендация включить непроверенный флаг.

## Что реализовано

| Часть | Поведение |
|---|---|
| API | Только loopback, отдельный bearer-token каждого подключения, точные allowlist профиля/чата/темы/пользователя |
| Очередь | Подтверждение после SQLite commit, дедупликация, конфликт при повторном ID с другим содержимым |
| Исполнение | Один отправитель, проверка разрешений перед заданием, постоянные состояния и журнал переходов |
| Восстановление | Неизвестная отправка не повторяется; подтверждённые части не пересылаются заново |
| Значки | Детерминированный выбор по теме из реального каталога Telegram, учёт четырёх последних других тем, отбрасывание устаревших заданий |
| Голос | Детерминированная нормализация чисел, командный TTS-провайдер, Ogg/Opus, части ≤60 с, отдельная отправка каждой части |
| Hermes | Два публичных hooks, durable outbox и привязка к точному ходу; отсутствуют импорты внутренностей Hermes |
| Эксплуатация | CLI check/status/job/submit/work-once/serve, пример systemd unit, безопасный режим без отправки |

Модуль голоса v0.1 не воспроизводит контекстное LLM-преобразование существующего `voice-dual-reply`. Качество реального TTS ещё не проверено; провайдер явно задаёт оператор. Подтверждение Telegram относится к нашему голосу/значку, не к доставке текста Hermes.

## Проверить без подключения аккаунтов

```bash
cd /home/operator/workspaces/automation-integrations
python3 -m unittest discover -v
PYTHONPATH=. python3 ops/demo.py
```

Демо создаёт временные конфигурацию, токен и SQLite, запускает настоящий HTTP API, передаёт задания двух типов и ждёт `simulated`. После завершения временные файлы удаляются. Сеть используется только на loopback. Ни Telegram, ни TTS не вызываются.

Media-тест требует `ffmpeg` и `ffprobe`; при их отсутствии он явно пропускается. На SG его запускают только в отдельном staging-каталоге. Тест создаёт WAV с тишиной и проверяет реальные кодирование, длительность частей и multipart-запросы локальному HTTP-имитатору. Это не проверка натуральности голоса или настоящей доставки.

## Структура

- `automation_integrations/`: API, очередь, worker, два модуля, Telegram-коннектор и CLI.
- `bridges/hermes/`: устанавливаемый каталог штатного плагина Hermes.
- `examples/`: конфигурации без секретов и реальных адресатов.
- `ops/`: демо, пример systemd, проверка настоящим загрузчиком Hermes.
- `docs/CONTRACT.md`: протокол, гарантии, ограничения и добавление нового модуля.
- `docs/OPERATIONS.md`: запуск, диагностика, отключение и откат.
- `docs/COMPATIBILITY.md`: проверенная база и разрыв между загрузкой и функциональным паритетом.
- `docs/PROVENANCE.md`: происхождение числового нормализатора.
- `PUBLICATION.md`: состав и границы публичной копии.

## Следующий этап

Аудит официального `37dd129a` завершён: [варианты и предлагаемый Runs API прототип](docs/COMPATIBILITY.md#повторный-аудит-официального-main--03102026). Изолированный [Runs API прототип](docs/RUNS_PROTOTYPE.md) реализован и проверен на HTTP-обработчиках чистого Hermes с тестовым исполнителем. Добавлен localhost fixture ingress; проверена вся цепочка с настоящей моделью до simulated job. Добавлены [речевые адаптеры](docs/SPEECH_SMOKE.md): реальный ElevenLabs→Opus→Whisper прошёл проверку чисел и отрицания. Живой Telegram-вход и приёмка качества речи человеком остаются впереди.

Для чистого Hermes сначала получить поддерживаемый интерфейс достоверного происхождения ответа или выбрать другой официальный способ подачи сообщений с сохранением идентификаторов. Отдельный сервис эту информацию создать не может. До решения этого вопроса допустимы изолированные проверки и явная подача событий доверенным подключением, но автоматическое переключение рабочего Мерлина не подготовлено.

После этого — отдельная приёмка выбранного TTS и пилот на одной выделенной теме, с отключением прежнего владельца соответствующего действия. MAX, поиск истории и существующие рабочие расширения этой версией не заменяются.

## Грейф на Kronstadt: реестр API

Текущий выпуск `automation-api-catalog` 0.7.1: [реализация по документации и проверки](docs/API_FULL_RELEASE.md).
Для Яндекс Go, ЭТМ, Saby и Точки реализованы исполнители 211 из 233 описанных методов;
чтения, фильтры, пагинация, PDF и подтверждаемые бизнес-операции. Точные границы и
неоднозначные контракты отмечены в реестре. Документация скачана в
[датированный снимок](docs/api-snapshots/2026-10-04/README.md).

Канонический реестр — `registry/catalog.json`; индекс обновляется перед каждым ходом.
`integration_catalog` раскрывает схемы, `integration_read` выполняет чтение,
`integration_write` использует локальный черновик. Для заказов и отгрузок ЭТМ
достаточно прямого поручения владельца; отдельное сообщение с UUID не требуется.
Остальные операции сохраняют прежнее подтверждение владельца.
Успешный HTTP-ответ не подменяет проверку бизнес-результата. Для Wiren Board подготовлено
[дополнение управления](docs/WIRENBOARD_CLOUD.md): 10 чтений, 11 подтверждаемых операций
облака и одна составная команда через SSH. Отдельный новый черновик и сообщение владельца
подтверждают точные изменения; неизвестный исход не повторяется. Живые облачные изменения
не тестировались. Локальные отчёты проверки SSH содержат сведения об устройствах и не публикуются.
