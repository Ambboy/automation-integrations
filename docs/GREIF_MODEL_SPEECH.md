# Грейф: голосовые по 3–5 минут

Обновление 04.10.2026: `automation-speech-source` 0.4.1 сохраняет полный текст
ответа и отправляет речь отдельными OGG/Opus-файлами по **3–5 минут**, целевая
длительность около4 минут, максимум300с. Короткий ответ или последний остаток
могут быть короче3 минут; тишина для увеличения длительности не добавляется. Текст уходит
штатным путём сразу; автоматическая озвучка готовится в фоне. Голос и модель
ElevenLabs прежние. Код Hermes d440c5b59b42d23007ab725f646d3b472670f890 не изменён.

## Исправление подключения после обновления — 04.10.2026

В `automation-speech-source` 0.4.1 каждому экземпляру принадлежит отдельная,
стабильная внутри него callback-фабрика. Это позволяет штатному Telegram-адаптеру
подключить новый экземпляр: в Hermes d440c5b59 фабрики дедуплицируются по имени
плагина и `__qualname__`. Фабрика только сохраняет Bot и event loop, не добавляет
обработчиков Telegram. Если после reload транспорт ещё не привязан, входящий
owner-hook получает точный принимающий адаптер через публичные
`identity_of(event.source).adapter()` и вызывает `rewire_plugin_handlers`.
Резервный `gateway.adapters` разрешён только при выключенном multiplex; при
неопределённом маршруте в multiplex переподключение отклоняется. Нативный callback
снова передаёт плагину Bot и event loop. При невозможности подключения пишется
безопасная диагностика.

Сбой подтверждён в теме «Проверить условия генерации видео и изображений 11labs»:
голосовое принято в 16:13, ответ из 3032 знаков готов в 16:20, но задание озвучки
не появилось. Предыдущее обновление через reload в 16:07 создало новый плагин
без привязки к Telegram. Синтез ElevenLabs в этом ходе не запускался.

**Первую установку исправления активировать перезапуском свободного
`hermes-gateway.service`.** `reload-plugins` сам по себе недостаточен: повторная
загрузка тех же ключей плагинов может не вызвать повторное подключение адаптера.
Новый inbound-путь восстанавливает эту привязку при следующем запросе.
Поле `adapters_rewired` считает адаптеры и не доказывает вызов нашей фабрики.
Сначала проверить `active_agents=0` и отсутствие фоновых speech jobs, затем
остановить только gateway, применить подготовленное обновление, запустить gateway
и проверить запись `Wired native handlers from plugin 'automation-speech-source'`.
Ядро не изменяется.

Установка: `python3 -m ops.greif_voice_reload_release prepare|apply|rollback`.
Меняются только `delivery.py` и `plugin.yaml`; конфигурация и provider сохраняются.
Резерв и квитанции: `short-voice/update-20261004-voice-reload`.
После rollback тоже требуется запуск/перезапуск свободного gateway. Для полного
отката сначала выполнить voice-reload rollback, затем length, timeout180 и
short_voice_release в ранее описанном порядке. SHA-проверки защищают поздние правки.

## Подготовка и разбиение

Сохранена принятая 03.10 подготовка: основная модель профиля превращает исходный
ответ с контекстом в речевой сценарий, затем отдельным вызовом сверяет факты,
числа, отрицания, условия и порядок действий. Это вероятностная модельная сверка.
Весь сценарий проверяется до оплаты: до 20000 знаков, без цифр. Разбиение по
предложениям/словам даёт запросы ElevenLabs не более 600 знаков вместо прежних 3000.
Запросы последовательные, без автоматических повторов. Ошибки сети сохраняют
безопасную категорию timeout/dns/connection/transport, без текста и ключей.

По следующему поручению 04.10 ожидание HTTP ElevenLabs увеличено с 60 до **180
секунд** в исходном и установленном `speech.py`. Это таймаут блокирующей операции
сокета, а не длительность аудио или строгий общий срок запроса. Минутный лимит
аудио у ElevenLabs не подтверждён. Прежняя нарезка до55с заменена по новой просьбе.
Старые ошибки `speech_provider_outcome_unknown` не позволяют доказать таймаут
исходного сбоя; новая диагностика сохраняет категорию причины.

Общий бюджет фоновой подготовки —5400с; rewrite/verify —230с; отправка одного
голосового в Telegram —90с. Явный `text_to_speech` дополнительно ограничивается
штатным Hermes до420с на весь инструмент, поэтому очень медленное многочастное
озвучивание может не уложиться. Эти независимые лимиты не менялись.

Все WAV коротких запросов объединяются в исходном порядке в общую PCM-запись.
Из неё получаются более длинные сообщения; границы между WAV предпочтительны,
пока они позволяют выдержать диапазон и сохранить остаток. Если необходимо,
граница проходит по сэмплам внутри фрагмента. Сохранены все сэмплы и весь хвост;
ускорения, удаления звука и искусственного удлинения нет. Каждая итоговая часть
отдельно кодируется в OGG/Opus и измеряется ffprobe: максимум300с. Ограничение
запроса ElevenLabs до600 знаков не определяет размер сообщения Telegram.
`tts-parts` публикует manifest только после успеха всех частей. При ошибке временное
аудио этой попытки удаляется и плагин уведомляет пользователя. Маленькие запросы
снижают риск таймаута, но не исключают отказы сети/провайдера.

## Подключение и доставка

У command TTS и TTSProvider текущего ядра выход — один файл; native TTS объединяет
части по размеру без лимита секунд. Поэтому многократная доставка реализована
в существующем плагине через публичные интерфейсы:

- register_platform_handler получает PTB Bot; pre_gateway_dispatch сохраняет
  точные chat/thread/user/message, pre_llm_call связывает их с session/turn.
  Task-local ContextVars обязательны; process environment не даёт права доставки.
  Cached session без SESSION_ID поддерживается при совпадении исходного сообщения.
- transform_llm_output только ставит работу в очередь и возвращает None.
  История и текст не меняются; долгий синтез не занимает hook.
- Части идут по порядку в исходную тему с reply anchor через публичный PTB send_voice.
  Это исключает native fallback voice→document после неопределённой отправки.
- Для явного text_to_speech публичный tool_execution middleware возвращает несколько
  файлов с MEDIA-тегами; доставка остаётся штатной. Совместимость JSON с нативным
  collector проверена. Ошибка middleware возвращает error, не запускает второй TTS.
- SQLite delivery_jobs дедуплицирует задания до оплаты и фиксирует число подтверждённых
  отправок. При ошибке/таймауте отправка не повторяется. Прерванные задания после
  перезапуска автоматически не возобновляются.

Native auto-TTS для telegram:100001 отключён; этим занимается плагин с исходным
режимом voice_only. Команды владельца обрабатывает плагин: /voice on — ответы на
голосовые, /voice tts — все ответы, /voice off, /voice status. Настройка хранится
в delivery_preferences. Просьба «только текст» подавляет озвучку текущего хода.
/stop отменяет текущую тему; off/unload останавливают задачи и дочерние процессы.
Чужие пользователи, группы и дочерние агенты не допускаются.

## Откат

Для возврата к сообщениям до55с с сохранением HTTP timeout180с, после проверки
модельных и фоновых голосовых задач остановить только gateway:

```bash
sudo systemctl stop hermes-gateway.service
python3 -m ops.greif_voice_reload_release rollback
python3 -m ops.greif_voice_length_release rollback
sudo systemctl start hermes-gateway.service
```

На этой версии применять stop/start; один reload-plugins недостаточен.
SHA-защита блокирует затирание более поздних правок; данные и резерв сохраняются.
Для полного возврата к native TTS последовательность между stop/start:
сначала voice_reload rollback, затем voice_length rollback, timeout180/rollback.py и
ops.greif_short_voice_release rollback. Старый установщик сверяет SHA provider.
Прежний ops/greif_phase2_config.py rollback относится к phase2→phase1.
