## Программный интерфейс

`automation_integrations.runs.RunsHTTP(endpoint, token_file)` принимает только HTTP endpoint с буквальным 127.0.0.1 и явно заданным портом; секрет читается из абсолютного файла владельца с правами 0600. Прокси и перенаправления отключены. Это стендовый клиент; TLS/удалённые адреса пока не поддерживаются.

`RunsPrototype(state_dir, client, routes)` хранит состояние в приватном каталоге. Один экземпляр состояния закреплён за endpoint и учётными данными; их незаметная смена блокируется. Список маршрутов задаёт допустимые profile/platform/chat/user/thread. Подразумевается один заранее выбранный профиль API на клиент: поле profile в origin не переключает профиль Hermes. Вход trusted: это библиотека тестового стенда, не открытый сетевой приёмник Telegram.

- `submit(origin, text, mode="text")`: сохраняет вход; тот же ID сообщения с изменённым содержимым отвергается. Origin: profile, platform, chat_id, thread_id, user_id, message_id, message_type (`voice`/`text`). Text для голосового входа — уже готовая тестовая расшифровка, STT отсутствует.
- `step(turn_id)`: выполняет максимум один HTTP-запрос. Возвращает состояние, без фонового бесконечного цикла. Повтором после `retryable` и паузами управляет вызывающий код; production scheduler с backoff ещё не реализован.
- `snapshot(turn_id)`: читает приватный результат, включая текст и исходный origin. Не отдавать его как публичный status API.
- `publish_dry_run(turn_id, store, connection, policy)`: передаёт проверенное событие в существующий Store только с dry_run=True. Повтор после сбоя между commit и сохранением квитанции использует тот же event_id и не создаёт второго задания.

Режим ответа передаётся явно. Прототип не определяет намерение «только текстом» по свободному тексту: будущий входной коннектор обязан передать mode=text. Голос возможен только при message_type=voice и mode=voice; обычный текст и пустые/служебные ответы не создают голосовых событий. Текстовый результат сохраняется, но транспорт отправки текста в этой реализации отсутствует. Модуль значков остаётся доступен через прежнее topic.observed, новый клиент не выдумывает тему из ответа модели.

## Привязка и восстановление

Ключ разговора содержит профиль, платформу, чат, тему и пользователя; message_id добавляется для ключа запроса. Результат определяется по сохранённому run_id, а не по «последнему активному чату». Перед публикацией проверяются run_id и session_id из ответа Hermes. Неожиданная смена session_id, включая неучтённую ротацию сессии, блокирует доставку; миграция сессий пока не реализована.

Тело POST и Idempotency-Key сохраняются до сети и не меняются при повторе. Неизвестное принятие можно повторить только в течение 23 часов с первого обращения — меньше документированного срока хранения ключа. После этого outcome_unknown; новый запуск автоматически не создаётся. Исчезновение известного run_id, неизвестный формат статуса и несоответствие идентификаторов тоже не приводят к новому запуску.

В одном разговоре следующий запрос ждёт успешного завершения предыдущего и использует сохранённые пары user/assistant. Между разговорами вызовы step можно чередовать. flock запрещает двум драйверам одновременно обрабатывать одну базу. Failed/cancelled/interrupted/outcome_unknown блокируют последующие ходы этой линии до ручного разбора; интерфейс разбора и кнопка stop пока отсутствуют. Waiting_for_approval не разрешается автоматически. При лимите истории 120 КБ клиент останавливает новый запрос, а не незаметно обрезает контекст.

## Ограничение фоновых продолжений

В проверенном исходнике `gateway/platforms/api_server_runs.py` допуск detached-доставки вычисляется по истинности conversation_history. Поэтому пустого массива недостаточно: первый запрос содержит непустой system-элемент истории, последующие дополняют его завершёнными парами. Native-тест проверяет `launch.session_history_delivery is False` на границе перед исполнителем.

Это доказывает выбор ветки API, но не фактическое выполнение всех фоновых инструментов настоящей моделью. Непрошенные продолжения, чтение поздних результатов из истории, подтверждения человеком и перенос нынешней автономности Мерлина не реализованы. Для production потребуется отдельная приёмка этих возможностей. [Официальное описание Runs API](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server/#runs-api-streaming-friendly-alternative).

## Тестовый входной коннектор

`automation_integrations.ingress.running_ingress(prototype, profile, token_file)` поднимает временный HTTP-сервер только на 127.0.0.1. `POST /v1/fixtures/telegram` принимает JSON `{update: {update_id, message}, reply_mode, transcript?}` с отдельным Bearer-токеном. Это доверенный стендовый ввод, не зарегистрированный Telegram webhook. Профиль назначается сервером, отправитель/чат/тема проходят allowlist RunsPrototype. Боты, неподдерживаемые updates, пересланные сообщения и voice без явной расшифровки отвергаются. По умолчанию ответ текстовый; voice разрешается только явно для voice-входа. Приём не запускает модель; драйвер вызывает step отдельно.

Native-тест теперь проходит через этот HTTP ingress, затем реальные Runs API handlers Hermes и dry-run очередь. Живой smoke находится в `ops/live_runs_smoke.py`, требует явного --execute, пути существующего профиля и checkout. Он создаёт временный private HERMES_HOME, копирует только выбранную авторизацию без refresh_token, отключает инструменты/плагины, делает один синтетический запрос; рабочую авторизацию и профиль не перезаписывает. Весь временный профиль удаляется при нормальном выходе. Внешнее принудительное завершение процесса может оставить временный каталог: его следует проверить отдельно. Telegram и реальный TTS в этом smoke не используются.
