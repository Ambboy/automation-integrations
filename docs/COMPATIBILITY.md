## Что нужно для полного переноса на чистый Hermes

Поддерживаемые события должны предоставлять достоверные source/profile/chat/thread/user/message/session/turn, тип исходного сообщения и связь с внутренними продолжениями. После появления официального контракта меняется только bridge; сервис и модули сохраняют протокол. Альтернатива — официальный входной адаптер, которому поручена идентичность сообщений; это отдельная работа с владением транспортом.

Нельзя заменить это чтением `.env`, хвостов логов, угадыванием chat_id по тексту или monkey patch. Существующий production пока сохраняет прежние расширения; проект не добавляет новых патчей к ядру.

## Воспроизведение native-проверки

Из изолированной копии Hermes:

```bash
HERMES_PYTHON=/absolute/path/to/existing/test-environment/venv/bin/python \
  scripts/run_tests.sh /absolute/path/to/automation-integrations/ops/compat_tests/test_hermes_bridge_contract.py -q
```

Тест создаёт временный HERMES_HOME, устанавливает туда bridge, проверяет настоящую загрузку/вызов hooks/выгрузку, отсутствие исходящих событий без origin и остановку фонового отправителя. Основная конфигурация, реальные токены и gateway не используются. Результат этого теста не доказывает, что исходящий голос работает на чистом Hermes: именно эта возможность недоступна без необходимой привязки.

### Варианты без патчей ядра

| Вариант | Применимость | Ограничение |
|---|---|---|
| Текущий hook bridge | Минимальная установка рядом с Hermes | На новом официальном SHA необходимый origin тоже отсутствует; автоматический голос остаётся заблокирован |
| Gateway hooks agent:start/end | Аудит и простые реакции | По документации тексты ограничены 500 символами; нет полного необходимого контракта происхождения |
| Собственный платформенный адаптер | Штатная регистрация платформы, полный контроль входа/выхода | Придётся поддерживать транспорт; универсальная привязка внутренних продолжений не доказана |
| Собственный Relay-коннектор | Внешний транспорт, адресованные исходящие действия | Контракт экспериментальный; reply_to необязателен; строгий паритет голоса на фоне не доказан |
| Собственный входной сервис + Runs API | Мы сохраняем origin до вызова Hermes и связываем его с run_id | Меняется владелец Telegram-входа; фоновые продолжения требуют отдельного клиентского механизма |

Relay остаётся возможным решением для владения транспортом, но не быстрым исправлением существующего bridge. [Официальный контракт Relay](https://hermes-agent.nousresearch.com/docs/developer-guide/relay-connector-contract/) и [gateway hooks](https://hermes-agent.nousresearch.com/docs/user-guide/features/hooks/).

### Рекомендуемое направление следующего прототипа

Для самостоятельной общей системы предпочтителен **наш входной сервис → официальный Runs API Hermes → наши модули → доставка**. Это проектное предложение, ещё не реализованный и не принятый к переключению путь.

Наш сервис сохраняет origin, режим ответа и ключ идемпотентности ДО запроса. Он связывает возвращённый run_id с исходным событием; session_id используется для истории разговора, но не как замена ID сообщения. Только итоговый ответ порождает reply.completed; промежуточные сообщения не озвучиваются. Иконки используют отдельное topic.observed. Уже написанные очередь, обработчики и исходящий Telegram-транспорт остаются применимы.

Runs API документирует ключ идемпотентности, опрос статуса и SSE. Поздний detached-результат не открывает завершённый поток заново: он сохраняется в истории сессии; следующий ход контролирует клиент. Поэтому нельзя обещать автоматические фоновые ответы через один SSE. Источник: [Runs API и detached results](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server/#runs-api-streaming-friendly-alternative).

Границы минимального прототипа:

1. Только изолированная тестовая конфигурация, искусственные сообщения, без Telegram-токенов и платного LLM. Проверить реальный API Hermes с подменённым исполнителем, затем отдельно согласованный живой пилот.
2. Проверить два чата/две темы, последовательные голосовые и текстовые сообщения, повтор POST после таймаута, рестарт клиента/сервера и конфликт ключа; один origin должен давать максимум одно задание доставки.
3. Проверить stop, interrupted, failed и ожидающее подтверждение; не запускать повторный ход автоматически при неизвестном результате или ожидающем решении человека.
4. Для поздних продолжений отдельно доказать публичную связь delegation/result с исходным origin. Если она недостаточна, первый прототип ограничить синхронным выполнением; не назначать фоновому ответу origin «последнего сообщения в чате».
5. До миграции определить единственного получателя Telegram updates и владельца каждого вида отправки. Новый сервис потребует собственных правил допуска, команд, медиа/STT и подтверждений — этого v0.1 пока не реализует. Второй poller того же бота не запускать.
