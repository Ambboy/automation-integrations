## Использование ботом

`integration_catalog(service="etm")` — карточка действующих адаптеров.
`integration_catalog(service="etm", view="capabilities", limit=10, offset=0)` —
страница полного реестра. `next_offset` указывает продолжение. `query` ищет по
назначению/имени/категории/маршруту. `capability_id` возвращает точный метод с
параметрами и схемой тела. В каждое начало модельного хода добавляется короткий
индекс и инструкция сначала обращаться к существующему API.

`integration_read` допускает только фиксированные операции чтения, а также
получение сессии ЭТМ/Saby для этих чтений. Изменения заказов, платежи, подписи,
отправки, регистрации МЧД, отчёты с генерацией и webhooks перечислены в реестре,
но не выполнялись и не имеют универсального исполнителя. Наличие GET не служит
самостоятельным разрешением: в адаптер включены конкретные изученные маршруты.

## Живые результаты

- Яндекс: компании, сотрудники, история/активные заказы, сведения о настоящем
  заказе, подразделения, центры затрат, администраторы, командировки. Исправлен
  старый неверный путь сведений о заказе: `/orders/info`.
- ЭТМ: вход, карточка/цена/остатки товара, производители, счета за период и позиции
  реального счёта. Поиск `/catalog` вернул HTTP 404 даже при рабочей сессии через
  российский выход. Не обозначать как отсутствие API или неверный пароль.
- СБИС: версия API, свои организации, список и чтение реального входящего
  документа. Для version нужен `Параметр: {}`, для организаций — `Фильтр: {}`:
  отсутствие этих аргументов давало HTTP 404, после исправления запросы успешны.
- Точка: счета/конкретный счёт, общие/конкретные остатки, карточные холды, список
  и чтение существующей выписки, клиенты, согласия, платежи эквайринга, подписки,
  ожидающие подписи платежи и поступления СБП. Список торговых точек эквайринга
  вернул HTTP 424; причину/доступность продукта не выводить из одного кода.
  Один запрос счетов получил network_unavailable, отдельная повторная проверка
  и зависимые запросы успешны. Автоматического retry бизнес-операций нет.

Проверки относятся к отдельным страницам/объектам, не полным выгрузкам. Пустой
успешный ответ подтверждает вызов, но не наличие сущностей. Платежи эквайринга,
подписки и СБП пока возвращают первую страницу по одной записи. Для счетов ЭТМ
диапазон ограничен 31 днём; входные даты ISO переводятся в DD/MM/YYYY. JSON >2 MiB
и очищенные результаты >60 KB отклоняются. Значения/подписанные ссылки очищаются.

## Российский выход ЭТМ

Для ЭТМ поддерживается явно настроенный обратный SOCKS через доверенный SSH-хост.
Публичный пример использует локальный listener `127.0.0.1:10929` и отдельные
системные учётные записи для туннеля. SSH ограничивается нужным forwarding,
проверкой host key и списком разрешённых API-направлений. Пример сетевых адресов
из диапазона документации: `192.0.2.1` и `192.0.2.2`; они не являются рабочими узлами.
Реальные адреса, ключи и сведения о маршруте хранятся в приватной конфигурации.

Private config содержит `etm_proxy`, а не копию ключа или паролей.

находятся в private state и registry; повторять чтения без причины не нужно.

Перед установкой сохранены исходные файлы/хеши и gateway state в
`~/.local/share/automation-integrations/greif/api-catalog/update-20261003-capabilities`.
`PYTHONPATH=. python3 ops/update_catalog_release.py apply` обновляет только файлы
плагина/исполнителя/реестра; config.yaml не редактируется. Затем штатный idle restart.
Откат: та же команда с `rollback`, проверка хешей и отдельный idle restart. Более
поздние изменения автоматически не перезаписываются. Исходный полный откат
`greif_catalog_config.py rollback` относится к первой установке, не к этому обновлению.

Для снятия только нового туннеля: остановить/disable `greif-etm-egress.service` на
Алёне; сохранить ключ/резерв; удалить только новый drop-in и dedicated ключевой
файл на Kronstadt, `sshd -t` и reload ssh. Не удалять другие AllowUsers/ключи/GRE и
не перезапускать VPN. Политика прямого запроса ЭТМ останется fail-closed.
