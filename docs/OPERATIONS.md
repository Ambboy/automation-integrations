# Эксплуатация v0.1

## Размещение

Канонический исходник: `/home/operator/workspaces/automation-integrations` на Kronstadt. Изолированная проверочная копия на SG: `/home/operator/workspaces/automation-integrations-compat/project`. Ни одна из них не включена в рабочий Hermes. Runtime SQLite, аудио, токены и логи должны находиться вне исходников и vault.

Зависимости сервиса: Python 3.11+ со стандартной библиотекой. Для реального голоса нужны FFmpeg, FFprobe и настроенный командный TTS. Установка Python-пакетов в окружение Hermes не требуется.

## Подготовка отдельного пилота

Это инструкция будущего запуска, не утверждение о выполненном production-deploy.

1. Выбрать точные профиль, чат, пользователя и одну отдельную тему; определить единственного владельца каждого исходящего действия.
2. Скопировать `examples/config.json` во внешний приватный каталог, заменить placeholders. Оставить `dry_run:true`. Состояние в отдельном каталоге `0700`.
3. Создать отдельный случайный bearer-token подключения, сохранить в owner-only файл `0600` без вывода в чат. Telegram-token нужен только для `dry_run:false`; получить его штатно из Vaultwarden в защищённый файл. Не копировать всю `.env` Hermes.
4. Выполнить `check`, запустить сервис в foreground и проверить `/health`, демо-события и состояния `simulated`.
5. Проверить origin-контракт хоста. На чистой базе 298df082 остановиться на диагностике: автоматический голос не поддержан. На проверенном хосте установить bridge штатным механизмом Hermes в отдельный тестовый профиль; существующий профиль не перезаписывать.
6. Перед реальными отправками требуется отдельная приёмка TTS и согласование пилота. Пример systemd unit предоставлен, но не установлен.

## Команды

```bash
python3 -m automation_integrations.cli --config /absolute/path/config.json check
python3 -m automation_integrations.cli --config /absolute/path/config.json serve
python3 -m automation_integrations.cli --config /absolute/path/config.json status
python3 -m automation_integrations.cli --config /absolute/path/config.json job JOB_ID
python3 -m automation_integrations.cli --config /absolute/path/config.json submit \
  --connection hermes-server --event-file /absolute/path/event.json
python3 -m automation_integrations.cli --config /absolute/path/config.json work-once
```

`submit` — доверенная локальная административная операция. Она проходит те же проверки scope, но не требует HTTP bearer. `work-once` использует тот же worker lock и не запустится одновременно с сервисом. `check` проверяет конфигурацию/права секретных файлов/доступность executable в live-режиме; это не сетевой health-check провайдера.

Проверка systemd файла перед установкой: `XDG_RUNTIME_DIR=/run/user/$(id -u) systemd-analyze --user verify ops/automation-integrations.service`. Пути нужно привести к выбранному размещению. Каталог `ReadWritePaths` должен существовать до старта. Production-службы Hermes, VPN и polling не перезапускаются ради проверки этого сервиса.

## Ошибки и границы восстановления

`outcome_unknown` нельзя превращать в повторную отправку без выяснения результата. При timeout HTTP-приёма bridge повторяет **тот же event**, сервис дедуплицирует. При timeout отправки Telegram сервис **не повторяет** запрос. Это разные границы.

`partial` сохраняет квитанции успешных частей. `failed` может означать неподдерживаемый текст, отсутствующий TTS, отозванный маршрут или подтверждённый отказ Telegram. В журнале сохраняются безопасные коды, не stderr провайдера и не URL с токеном. Внешние алерты и автоматические сообщения об ошибке в чат пока не реализованы: оператор видит их через CLI/API.

Bridge хранит outbox в отдельном SQLite; `accepted` означает приём задания сервисом, не его доставку. При недоступности сервиса outbox сохраняется, повтор admission с задержкой до 60 секунд. Ошибки 400/401/403/404/409/413 становятся `rejected` и требуют исправления конфигурации/контракта. Автоматическое редактирование rejected-пакетов отсутствует.

Настройки и токены перечитываются при перезапуске. Сначала отключить/остановить bridge, затем завершить текущую отправку и остановить сервис. После запуска с новой конфигурацией маршруты перепроверяются для queued-заданий. Не считать редактирование JSON немедленным отзывом доступа в уже работающем процессе.

## Данные, отключение, откат

SQLite содержит тексты исходных событий; артефакты голоса остаются в приватном state-dir. Автоматическая очистка/срок хранения пока не реализованы. Для длительного запуска нужна политика retention и контроля диска; небольшие пилоты можно завершать сохранением нужных квитанций и отдельным решением об удалении состояния.

Отключение: убрать `automation-bridge` из enabled в тестовом профиле штатным способом и остановить только новый сервис. Выгрузка bridge закрывает его отправителя. Unit можно отключить/удалить; пользовательские SQLite, аудио и токены не удалять автоматически.

Откат версии: остановить новый сервис, сохранить state-dir, вернуть предыдущий commit приложения, проверить совместимость SQLite. Не откатывать БД поверх квитанций более новых отправок. При удалении проекта не затрагивать чужие репозитории, профиль Hermes и авторизации Telegram.

Production-переход, параллельное владение иконками/голосом и live E2E с реальными пользователями этой работой не выполнялись.
