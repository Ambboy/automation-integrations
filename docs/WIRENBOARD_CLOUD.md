# Wiren Board Cloud — подключение Грейфа

Пятый сервис общего каталога, `service=wirenboard`. Первые четыре — Яндекс Go,
ЭТМ, СБИС/Saby и Точка. Исходники этой доработки находятся в отдельной ветке
`wirenboard-cloud-api`, worktree `/home/operator/workspaces/automation-integrations-wirenboard`:
во время работы в основном каталоге параллельно расширялись остальные API.

## Использование

```json
{"service":"wirenboard"}
```

Передать в `integration_catalog`. Затем, например, в `integration_read`:

```json
{"service":"wirenboard","operation":"controllers","params":{"page_size":20,"page":1}}
```

Доступ сохранён в существующем контуре владельца: личный Telegram, проверенный
нативный контекст текущего сообщения. Полный реестр — `view=capabilities`,
`service=wirenboard`; параметры метода — по `capability_id`.

| Операция | Что возвращает |
|---|---|
| me | Текущий профиль |
| organizations | Доступные организации |
| controllers | Страница контроллеров с фильтрами организации, поиска, серийного номера |
| counters | Общие счётчики контроллеров |
| controller | Карточка и состояние агента контроллера |
| groups | Дерево групп выбранной организации |
| group | Карточка существующей группы |
| diagnostic | Состояние уже существующей диагностики |
| last_metrics_time | Время последней системной метрики |
| metrics | Значения одной системной метрики за интервал до 24 часов |

У `controllers` числовой `pagination.next_page`; фильтры и `page_size` сохраняются
при обходе. Полнота достигнута при `has_more=false`. Ссылки провайдера не переходятся
автоматически и не передаются инструменту как адрес следующего запроса.
`metrics` требует `serial_number`, `name`, `start`, `stop`. Допустимые имена:
`disk_free_data`, `disk_free_root`, `load15`, `mem_available`; даты ISO8601 с часовым
поясом. Ограничение 24 часа — локальное ограничение адаптера.

В реестре остаются 72 метода официальной схемы. Реализованы 10 операций чтения,
11 операций управления облаком и составная `controller_exec`. Последняя использует
документированный метод SSH-туннеля и затем одну команду на контроллере; отдельного
REST-метода shell у облака не заявляется. Метрики ОС не являются произвольными
MQTT-каналами; исправный облачный агент не доказывает исправность оборудования.

## Управление

Изменения доступны через отдельный `integration_write`. `prepare` читает текущее
состояние и создаёт preview с точной целью и параметрами, без изменения устройства:

```json
{"action":"prepare","service":"wirenboard","operation":"controller_update","params":{"serial_number":"SERIAL_FROM_CONTROLLERS","fields":{"description":"Новое описание"}}}
```

В примере требуется настоящий серийный номер из `controllers`. После показа полного
preview владелец отправляет **новое нативное сообщение** `ПОДТВЕРЖДАЮ <draft_id>`
в том же личном контексте. Подтверждение из истории, текста команды или от модели
не принимается. Затем `integration_write` получает `action=execute` и `draft_id`.
Срок действия — 10 минут; подтверждение связано с аккаунтом, контекстом, объектами
и параметрами. При изменении существенных полей после preview нужен новый черновик.

| Операция | Параметры и назначение |
|---|---|
| controller_update | `serial_number`, непустой `fields`: description, latitude, longitude, userDefinedData, metricsEnabled, metricsSendIntervalSeconds |
| request_diagnostic | `serial_number`; запрос сбора диагностики |
| service_add | `serial_number`, `port`, необязательный `name` |
| service_update | `serial_number`, `port`, `fields.name`; порт существующего сервиса не меняется |
| service_delete | `serial_number`, `port` |
| group_create | `organization_id`, `name`, необязательный `parent` (UUID/null) |
| group_update | `id`, непустой `fields`: name и/или parent; parent=null переносит на верхний уровень |
| group_delete | `id`; preview включает текущую иерархию группы |
| group_attach | `id`, `controllers` — серийные номера контроллеров той же организации |
| group_detach | `controllers` — серийные номера |
| controller_delete | `serial_number`; удаление контроллера из облака |
| controller_exec | `serial_number`, точный `command` как argv-массив; timeout 1..30 секунд, по умолчанию 30 |

Точные схемы находятся в `integration_catalog(service=wirenboard).write_operations`.
Обновление контроллера не принимает `firmwareVersion`, поля состояния, серийный
номер или смену организации. Координаты — null или значения с точностью до 7 знаков:
широта −90..90, долгота −180..180. Метаданные — до 100 пар `label`/`value`,
интервал метрик — 60..240 секунд. Порт сервиса — 1..65535; attach/detach принимают
до 20 уникальных контроллеров. Самоссылка и циклы родительских групп запрещены.
Команда содержит 1..64 аргумента без NUL; пустой первый аргумент запрещён.

Перед отправкой повторно проверяются актуальные поля и идентичность: id,
serialNumber и организация контроллера, id и организация группы. Состояние
`submitting` сохраняется до сети. После единственной отправки отдельные GET
сверяют результат: поля контроллера, коллекцию сервисов, дерево групп или группу
каждого выбранного контроллера. Ответ на создание группы не содержит id, поэтому
успех определяется единственной новой подходящей группой в дереве до/после.
Запрос диагностики подтверждает наблюдение нового запроса, а не готовность архива.

`accepted_unverified` означает, что ожидаемое состояние ещё не подтверждено.
`outcome_unknown` означает неопределённый исход: не повторять команду/мутацию и не
создавать заменяющий черновик автоматически. `action=status` с `draft_id` сверяет
облачное состояние чтением; не повторяет отправку. Эти состояния сохраняются
между процессами и перезапусками. Для `controller_exec` нулевой exit code означает
завершение команды; эффект на оборудовании требует проверки по конкретной задаче.

Активация и перенос контроллеров между организациями, участники, профиль,
безопасность аккаунта и скачивание диагностического архива отдельными REST-адаптерами
не реализованы. Нет произвольного API URL/метода или самостоятельной выдачи туннеля
в модель. SSH-ключи, URL и параметры доступа остаются внутри исполнителя.

## Авторизация и сеть

Токены берутся из существующей записи Vaultwarden
`Automation credential — 30_Services/wirenboard/credentials.env`. Значения не
попадают в каталог, аргументы процесса, отчёты или Obsidian. Пароль облачного аккаунта
и recovery codes исполнитель не использует. Рабочая авторизация — `Bearer`; это подтверждено
реальным чтением, хотя OpenAPI описывает `Token`.

В `private.json` добавлены только ссылка на запись и
`wirenboard_transport=ssh:example-ssh-host`. Прямое соединение Kronstadt→облако давало
таймаут. Используется существующий доверенный SSH-хост `example-ssh-host`: короткий
запрос с JSON через stdin, HTTPS только к `https://wirenboard.cloud/api/v1`,
проверка сертификатов, без redirects, proxy и произвольного адреса. Новых VPN
и фоновых сетевых служб не создавалось. Отказ SSH не вызывает
перехода на другой маршрут. Для среды с прямой связью допустим явный `direct`.

`controller_exec` запрашивает краткоживущий SSH-туннель только внутри подтверждённого
выполнения. Учётные данные устройства используются внутренне: существующий
root/factory-доступ либо явно настроенная общая SSH-запись Vaultwarden. Модель
не получает их и не передаёт через параметры операции. Доступность облачного API
не доказывает успешную SSH-аутентификацию на устройстве.

Кэш находится в закрытом `api-catalog/state/wirenboard-session.json` (0600).
Обновление сериализовано `flock`; access и возможный новый refresh сохраняются
атомарно с fsync файла и каталога. Перед refresh записывается `refresh_pending`.
При неопределённом исходе старый refresh автоматически не повторяется.
Не удалять кэш при обновлении/откате: исходный refresh из Vaultwarden уже мог
ротироваться, и кэш содержит актуальную пару.

`refresh_outcome_unknown` — неопределённый исход обновления сессии;
`reauthentication_required` — требуется восстановление сессии оператором.
Новая пара токенов в Vaultwarden меняет fingerprint и позволяет начать новую
сессию. Ошибки сети, доступа, размера ответа и кэша выдаются отдельно.

## Проверка

Локальная проверка охватывала операции чтения, пагинацию и отдельную команду SSH.
Подробные отчёты с организацией, идентификаторами устройств и результатами доступа
хранятся приватно и не входят в эту публикацию. Успешное чтение облачного API
не доказывает SSH-доступ к каждому устройству. Изменения облака вживую не выполнялись;
их права и результаты остаются непроверенными. Реализация проверяется локальными тестами.

```bash
python3 -m unittest discover -q
python3 ops/wirenboard_safe_live.py --execute --config <private.json> --report <private-report.json>
```

## Установка и откат

Предыдущий выпуск чтения устанавливался через `ops/wirenboard_release.py`.
Его `prepare` создавал staged/backup снимки конкретных файлов;
`apply` проверял все исходные SHA, конфигурацию и
`active_agents=0` до первой записи. Существующие API и `config.yaml` не являются
целями изменения, кроме общего runner/каталога/plugin schema с добавлением WB.
Gateway перезапускается отдельно после проверки установленной цепочки.

Резерв: `~/.local/share/automation-integrations/greif/api-catalog/update-20261004-wirenboard`.
Откат из этого worktree: `python3 ops/wirenboard_release.py rollback`, затем
отдельный перезапуск gateway при отсутствии активных задач. Более поздние
изменения установленных файлов блокируют откат: сначала требуется сверка.
Ротированная сессия и receipts сохраняются при откате.

Выпуск управления установлен 04.10.2026: plugin **0.7.0**, каталог
**2026-10-04.3+etm-checkout.1+wb-control.1**. 321 unit test и 1 native contract
прошли. Установленный native инструмент подготовил controller_update чтением
актуальной цели и отклонил execute без подтверждения (`owner_confirmation_required`).
Изменений контроллера не было. После idle restart gateway PID 308462,
running/Telegram connected; все 10 установленных SHA совпадают, остальные
18 файлов проверенной базы и config.yaml сохранены. Четыре бизнес-интеграции,
включая актуальный ETM checkout, сохранены. Новый пользовательский ход в Telegram
после установки пока не наблюдался.

Резерв управления: `api-catalog/update-20261004-wirenboard-control`.
Откат: `python3 ops/wirenboard_control_release.py rollback`, затем отдельный
idle restart. SHA-проверка запрещает затирать более поздние изменения. Кэш
ротированной сессии и записи `state/wirenboard-writes` не удаляются.

Явный отказ SSH до отправки команды имеет статус rejected: после исправления
доступа можно подготовить и подтвердить новый draft. Неизвестный исход после
отправки повторять нельзя. Публичный вывод ограничен полным JSON-ответом до
60000 символов и помечается stdout_truncated; полный очищенный вывод остаётся
в закрытой записи исполнения.

проверенное право аккаунта.
