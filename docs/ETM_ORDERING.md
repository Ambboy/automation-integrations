# Оформление заказов ЭТМ

Грайф использует `integration_write` с `service=etm`, `operation=order_checkout`.
Сценарий получает живые товары/цены, магазин, договор и способы оплаты, сохраняет
точное предложение и по поручению владельца оформляет заказ без отдельного
сообщения с кодом подтверждения. Номера документов
назначает ЭТМ. Каждый итоговый документ, включая результаты разделения заказа,
перечитывается и сверяется с товарами, количеством, получателем, магазином,
суммой и договором. Принятие заказа не означает готовность к выдаче.

## Почему раньше не работало

В реальном заказе 04.10.2026 добавление товара прошло, но ЭТМ вернул строку
корзины с `selected: false`. Исполнитель пропускал штатный выбор строки перед
оформлением. Теперь он проверяет состав и условия корзины, выбирает только
нужные строки через `POST /basket/<nn>/edit`, перечитывает корзину и проверяет
результат перед заказом. Подготовка остаётся чтением и допускает явно
невыбранную строку; неизвестный статус выбора не принимается за корректный.
Поле `PartNum` оказалось необязательной подписью партии в интерфейсе ЭТМ:
его пустое значение больше не блокирует допустимое распределение.
Источники и ограниченная живая проверка:
ETM_BASKET_SELECTION_EVIDENCE.json (локальный отчёт; в публичную копию не входит).

Установленная карточка ЭТМ описывала только чтение. Затем общий исполнитель
добавил заказ на основе документа, но создание самого документа оставалось
заблокировано: OpenAPI содержит `schema: null` у `/invoice/create`. Полный
контракт опубликован отдельно в руководстве ЭТМ «Работа с заказами» от
24.01.2025. Теперь он поддержан с сохранением происхождения и хеша документа.

Для обычных закупок используется API кабинета `/api/ipro/basket/order`: именно
он поддерживает штатный номер ЭТМ и выбранный способ оплаты. Публичный
`/invoice/create` требует видимый номер заказа клиента, а `/invoice/{id}/order`
не выбирает оплату и договор. Эти различия отражены в карточке, а не скрыты
за общим обещанием поддержки API.

## Инструменты

```json
{"service":"etm","operation":"checkout_options","params":{"region":"34","pickup_store":"29100"}}
```

Это чтение доступных магазинов, договоров и способов оплаты. На проверке
04.10.2026 `34` — Волгоград, `29100` — Университетский проспект, 85. Номер
магазина и доступность проверяются при каждой подготовке и перед отправкой.
Остатки по публичному `/goods/{id}/remains` могут относиться к Самаре из
настроек аккаунта; их нельзя выдавать за наличие в выбранном магазине.

```json
{"action":"prepare","service":"etm","operation":"order_checkout","params":{"items":[{"code":"6510970","quantity":100}],"region":"34","pickup_store":"29100","payment_method":"bill","pay_type":"bill","allow_supplier_order":true}}
```

Подготовка только читает кабинет. Она показывает точный состав, сумму/предел
суммы, юрлицо, магазин, договор и способ оплаты. В конфигурации Грейфа включено
`etm_order_authorization: owner_command`: обычного поручения владельца в личном
Telegram достаточно. При `confirmation_required=false` Грейф сразу вызывает
`execute` для того же `draft_id`; копировать UUID или посылать второе сообщение
не требуется. Привязку к сообщению создаёт нативный hook после проверки владельца,
она не принимается из аргументов модели. Вопросы о цене и наличии остаются чтением.
Отдельно уточняются только отсутствующие условия заказа. Вне этой политики
`confirmation_required=true` сохраняет прежнее подтверждение.

`continuous_cut=true` задаётся только при явном требовании владельца получить
один отрезок, а не из-за самого количества в метрах. Проверяется одно физическое
распределение на всю длину и в заказ записывается требование отрезка; фактический
отрез не объявляется уже выполненным. При отсутствии бюджета владельца используется
свежая полная сумма корзины: округлённая цена единицы может отличаться от неё.
Явный бюджет владельца не повышается. `allow_supplier_order=true` допускает закупку
у поставщика и явно отображается в предложении; поручение только со склада
исполняется с `false`. Кратность и минимальная партия не разрешают увеличивать
заказанное количество самостоятельно.

Существующие посторонние строки корзины не очищаются. После разрешённого
добавления количество, выбор строк, распределение, магазин, договор, способ
оплаты и сумма проверяются повторно перед единственным оформлением.
Сетевой обрыв после отправки не вызывает повторный заказ. `status` читает
состояние прежнего черновика и сверяет сохранённые документы.

## Публичный API

Все 19 методов опубликованного OpenAPI имеют контракт/исполнитель;
авторизацией управляет транспорт. `invoice_create` принимает поля отдельного
руководства. Его `OrderNumber` не генерируется интеграцией. Действия `C`
(заменить заказ и прежние условия) и `D` (отказ) явно показаны в подтверждении.
Заказ по существующему документу, доставка, создание точки доставки,
комментарии и печать доступны в реестре отдельно.

Политика прямого поручения распространяется на `order_checkout`, `invoice_order`,
`invoice_delivery`, `delivery_point_create`, `invoice_print` и `invoice_create`
с функцией `P`/`A`. Замена/отмена `C`/`D` и операции остальных сервисов сохраняют
свои прежние правила. Неопределённый результат заказа или отгрузки блокирует
повторную отправку также при смене параметров или переходе между API кабинета
и публичным API. Сначала нужно выяснить результат прежнего запроса.

Исправлены два дефекта транспорта: повреждение кириллицы внешним JSON-экранированием
конфигурации curl и принятие верхнеуровневого `code:400` за успешный ответ.
Теперь требуется явный статус ЭТМ `200`, ошибки возвращают код провайдера.
Секреты и сессии остаются в памяти и stdin транспорта.

## Проверка и эксплуатация

Код: `etm_order.py` (API кабинета), `etm_workflow.py` (состояния заказа),
`etm_authorization.py` (политика поручения и защита от повторной отправки),
`etm_document.py` (контракт публичного создания). Реестр обновляется
`python3 -m ops.extend_etm_catalog`; общий `ops.sync_api_contracts` сохраняет
это расширение. Основные регрессии: `tests/test_etm_*.py`.

Локальные тесты проверяют выполнение заказа через имитатор, разделение
документов, отказы, изменение условий и восстановление без дублирования.
Живые проверки используют авторизацию и чтение через существующий российский
SOCKS. Для приёмки разработки реальные заказы не создаются, платежи не
инициируются. Успешная проверка чтения не доказывает фактическую запись.

Для выпуска 0.7.1 прошли 369 unit-тестов, один native contract и проверка
установленного навыка. Установленная нативная связка подготовила исходные
100 метров товара 5226932 на 1 549,40 ₽ с `confirmation_required=false`.
Проверены все 10 установленных файлов; gateway после перезапуска свободного
процесса подключён к Telegram. Размещение заказа и отгрузка вживую в ходе этой
приёмки не выполнялись. Отчёт: ETM_OWNER_COMMAND_VALIDATION.json (локальный отчёт; в публичную копию не входит).

Обновление 0.7.1 устанавливается последовательными командами
`python3 -m ops.etm_owner_command_release prepare` и
`python3 -m ops.etm_owner_command_release apply`. Исходные снимки и манифест
сохраняются в закрытом `api-catalog/update-20261004-etm-owner-command`.
Откат — `python3 -m ops.etm_owner_command_release rollback`; возвращаются код,
политика и инструкция навыка. SHA-проверка не допускает перезапись более поздних изменений.
После изменения плагина нужен перезапуск свободного gateway. VPN и транспортный
туннель не переключаются.
