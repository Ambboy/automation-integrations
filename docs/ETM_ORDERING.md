# Оформление заказов ЭТМ

Грайф использует `integration_write` с `service=etm`, `operation=order_checkout`.
Сценарий получает живые товары/цены, магазин, договор и способы оплаты, сохраняет
точное предложение и по поручению владельца оформляет заказ без отдельного
сообщения с кодом подтверждения. Номера документов
назначает ЭТМ для корзины. Для другого проверенного офиса используется публичный
API со стабильным номером клиентской заявки. Каждый итоговый документ, включая результаты разделения заказа,
перечитывается и сверяется с товарами, количеством, получателем, магазином,
суммой и договором. Принятие заказа не означает готовность к выдаче.

## Почему раньше не работало

В реальном заказе 04.10.2026 добавление товара прошло, но ЭТМ вернул строку
корзины с `selected: false`. Исполнитель пропускал штатный выбор строки перед
оформлением. Теперь он проверяет состав и условия корзины, выбирает только
нужные строки через `POST /basket/<nn>/edit`, перечитывает корзину и проверяет
результат перед заказом. Подготовка остаётся чтением и допускает явно
невыбранную строку; неизвестный статус выбора не принимается за корректный.
Поле `PartNum` оказалось необязательной подписью партии в интерфейсе ЭТМ:
его пустое значение больше не блокирует допустимое распределение.
Источники и ограниченная живая проверка:
ETM_BASKET_SELECTION_EVIDENCE.json (локальный отчёт; в публичную копию не входит).

Установленная карточка ЭТМ описывала только чтение. Затем общий исполнитель
добавил заказ на основе документа, но создание самого документа оставалось
заблокировано: OpenAPI содержит `schema: null` у `/invoice/create`. Полный
контракт опубликован отдельно в руководстве ЭТМ «Работа с заказами» от
24.01.2025. Теперь он поддержан с сохранением происхождения и хеша документа.

Для офиса, предложенного корзиной, используется API кабинета `/api/ipro/basket/order`: именно
он поддерживает штатный номер ЭТМ и выбранный способ оплаты. Публичный
`/invoice/create` требует видимый номер заказа клиента, а `/invoice/{id}/order`
не выбирает оплату и договор. Публичный маршрут передаёт настоящий номер
и дату договора при создании и проверяет его привязку перед резервированием.

## Межрегиональные заказы — 07.10.2026

Передача `city` при входе и в cookie не переключала регион авторизованной
сессии. Теперь `WebsiteClient` получает описание города из `/info/city/{id}`,
сверяет `/user/session/get`, при необходимости вызывает штатный
`POST /user/set` с `param=region`, `val=<class17>` и перечитывает сессию.
Успешный ответ этого setter содержит только `status`, без `data`; это
разрешено только для данного метода. После операции исходный регион
восстанавливается с проверкой. Запросы выполняются под общей блокировкой
закупок; права аккаунта и сохранённый фильтр `userCity` не меняются.

`checkout_options` различает подтверждённый регион, офисы корзины и найденный
в справочнике запрошенный офис. Отсутствие офиса в корзине не означает общего
запрета заказа в этом регионе. В живой проверке Ростов `61` / `ЮГРСТ`
переключается успешно, Батайск `25140` найден по адресу; корзина продолжает
давать другой список. Поэтому `order_checkout` выбирает публичный маршрут
до первой бизнес-записи. Смена маршрута после отправки запрещена.

Публичный маршрут:

1. Готовит состав, цены, точный офис, доступный способ оплаты и настоящий
   договор из `/user/profile`. Подготовка не создаёт документов и не меняет корзину.
2. Показывает `customer_order_number`: переданный владельцем номер либо
   стабильный `AI-<UUID черновика>` из нашей системы. Это номер клиентской
   заявки, а не выдуманный штатный номер ЭТМ. Он сохраняется в черновике;
   повторная подготовка того же намерения не создаёт новый номер.
3. После поручения владельца создаёт документ через `/invoice/create`,
   передавая `ContractNumber`, `ContractDate`, точные количества и цены.
   `DeliveryPoint.ILN` не заполняется кодом склада: это другой идентификатор.
4. Сразу сохраняет все ID, перечитывает состав, суммы, юрлицо, договор и
   доступное распределение. Подтверждение условий требуется до резервирования.
   Публичный `/invoice/{id}/order` получает точный `skl`; список офисов
   web-корзины не используется как запрет этого документированного параметра.
5. Проверяет все документы после возможного разделения: место выдачи,
   количества, сумму, договор, дату оплаты и статус. Созданная спецификация
   не выдаётся за оформленный заказ. Неопределённый результат не повторяется;
   `status` только перечитывает документы.

Наличие физического распределения и непрерывного отрезка проверяется отдельно.
Сам факт создания заявки не подтверждает готовность товара или выполнение
требований к заводской упаковке. Публичный API не выполняет оплату.

Если создание сразу вернуло принятый заказ, повторного резервирования нет.
Для требования складского наличия или непрерывного отрезка такой ответ
без доказательств физического распределения остаётся `accepted_unverified`.
При ошибке последующего чтения известные ID доступны в сохранённом `receipt`.
Текущая проверка места выдачи требует точного `st_dest`: у завершённой
отгрузки поле может измениться, поэтому старый документ может остаться
неподтверждённым этой проверкой. Это не доказательство неверной выдачи;
снимать проверку по одному совпадению склада-источника нельзя.

## Инструменты

```json
{"service":"etm","operation":"checkout_options","params":{"region":"34","pickup_store":"29100"}}
```

Это чтение доступных магазинов, договоров и способов оплаты. На проверке
04.10.2026 `34` — Волгоград, `29100` — Университетский проспект, 85. Номер
магазина и доступность проверяются при каждой подготовке и перед отправкой.
Остатки по публичному `/goods/{id}/remains` могут относиться к Самаре из
настроек аккаунта; их нельзя выдавать за наличие в выбранном магазине.

```json
{"action":"prepare","service":"etm","operation":"order_checkout","params":{"items":[{"code":"6510970","quantity":100}],"region":"34","pickup_store":"29100","payment_method":"bill","pay_type":"bill","allow_supplier_order":true}}
```

Подготовка читает кабинет и временно выбирает регион с восстановлением.
Она показывает точный состав, сумму/предел
суммы, юрлицо, магазин, договор и способ оплаты. В конфигурации Грейфа включено
`etm_order_authorization: owner_command`: обычного поручения владельца в личном
Telegram достаточно. При `confirmation_required=false` Грейф сразу вызывает
`execute` для того же `draft_id`; копировать UUID или посылать второе сообщение
не требуется. Привязку к сообщению создаёт нативный hook после проверки владельца,
она не принимается из аргументов модели. Вопросы о цене и наличии остаются чтением.
Отдельно уточняются только отсутствующие условия заказа. Вне этой политики
`confirmation_required=true` сохраняет прежнее подтверждение.

`continuous_cut=true` задаётся только при явном требовании владельца получить
один отрезок, а не из-за самого количества в метрах. Проверяется одно физическое
распределение на всю длину и в заказ записывается требование отрезка; фактический
отрез не объявляется уже выполненным. При отсутствии бюджета владельца используется
свежая полная сумма корзины: округлённая цена единицы может отличаться от неё.
Явный бюджет владельца не повышается. `allow_supplier_order=true` допускает закупку
у поставщика и явно отображается в предложении; поручение только со склада
исполняется с `false`. Кратность и минимальная партия не разрешают увеличивать
заказанное количество самостоятельно.

Существующие посторонние строки корзины не очищаются. После разрешённого
добавления количество, выбор строк, распределение, магазин, договор, способ
оплаты и сумма проверяются повторно перед единственным оформлением.
Сетевой обрыв после отправки не вызывает повторный заказ. `status` читает
состояние прежнего черновика и сверяет сохранённые документы.

## Публичный API

Все 19 методов опубликованного OpenAPI имеют контракт/исполнитель;
авторизацией управляет транспорт. `invoice_create` принимает поля отдельного
руководства. Прямой вызов требует точного `OrderNumber` владельца либо уже
сохранённого клиентского номера коннектора. Новый номер генерируется только
при первичной подготовке `order_checkout`, сохраняется и показывается владельцу;
при отмене, подтверждении или изменении берётся номер исходной заявки.

При `etm_order_authorization: owner_command` прямое поручение владельца
распространяется на документированные операции ЭТМ, включая отмену `D`,
изменение `C`, оформление по существующему документу и доставку. Повторное
согласие, UUID и отдельное сообщение не требуются для уже порученного действия
с известными условиями. Точное действие и объект остаются в `preview` и аудите.
Доступность метода сама по себе не является поручением выполнить его:
вопрос о цене не разрешает создание спецификации, просьба отменить не разрешает
отправлять сообщение менеджеру, а просмотр счёта не разрешает оплату.
Комментарий или изменение согласования выполняется только когда это входит
в явное поручение. Политики остальных сервисов не меняются.

Подготовка и чтение доступны независимо от незавершённой записи. Проверка
неопределённого исхода относится к конкретному намерению и затронутым документам;
отмена известной спецификации и выяснение её состояния не блокируются самим
фактом незавершённости исходного оформления. Повтор того же неизвестного POST,
в том числе с изменёнными параметрами либо другим маршрутом, не отправляется.

Исправлены два дефекта транспорта: повреждение кириллицы внешним JSON-экранированием
конфигурации curl и принятие верхнеуровневого `code:400` за успешный ответ.
Теперь требуется явный статус ЭТМ `200`, ошибки возвращают код провайдера.
Секреты и сессии остаются в памяти и stdin транспорта.

вложены в `path`, `query`, `body`, `headers` согласно реестру контрактов.
`checkout_options` и `order_checkout` — дополнительные составные сценарии
коннектора и в число 19 не входят. Наличие контракта означает возможность
вызова, но не является результатом живой проверки каждой бизнес-записи.

### Создание, подтверждение, изменение и отмена

Все четыре действия используют `POST /invoice/create`. Таблица руководства
ЭТМ на страницах 5–8 дополняет отсутствующую в OpenAPI схему тела запроса.
`OrderNumber` — номер заявки в системе клиента; ETM ID вида `1-…` — другой
идентификатор. `Seller.ILN=4660011519999` — опубликованная константа продавца,
а `DeliveryPoint.ILN` — GLN точки, не числовой код магазина.

| Функция | Поручение | До отправки | После отправки |
| --- | --- | --- | --- |
| `P` | Первично разместить заявку | Зафиксировать клиентский номер, состав и условия; проверить, нет ли уже отправленного того же намерения. | Сохранить все `data.id` и `data.ids[].docid`, прочитать каждый документ. Созданная спецификация — отдельный результат, не подтверждение резерва. |
| `A` | Подтвердить ранее размещённую заявку | Найти исходную заявку по точному клиентскому номеру и известным ETM ID. | Сверить фактическое состояние; функция `A` сама по себе не доказывает резерв или готовность к выдаче. |
| `C` | Изменить ранее размещённую заявку | Найти точный исходный объект; руководство допускает только «Спецификацию» или «Счёт на оплату». Показать новый состав и условия. | ЭТМ перезаписывает заявку и согласованные условия с новым ID. Сохранить связь старых и новых ID, сверить новые документы и состояние прежних. |
| `D` | Отказаться от ранее размещённой заявки | Взять исходный клиентский номер из сохранённой операции и сверить с живыми документами. Известный незавершённый заказ не запрещает собственную отмену. | Сверить отмену всех затронутых документов, завершить связанные локальные операции с сохранением истории; только после подтверждённого исхода выполнять зависимую замену. |

У `/invoice/create` нет параметра пути с ETM ID. Руководство не раскрывает
отдельный алгоритм сопоставления `D/C` с документом: коннектор связывает
клиентский номер с точными ID по сохранённому запросу, ответу и текущему чтению.
При нескольких совпадениях, в том числе после разделения, нельзя отменять
первую найденную строку и считать остальные закрытыми. Тело `D/C` собирается
по документированному контракту из исходных данных, без выдуманного номера
или случайной товарной строки ради прохождения схемы.

Смена города — это либо изменение подтверждённо допустимого документа,
либо подтверждённая отмена прежней заявки и новое первичное оформление.
Новый `P` не является способом скрыть ошибочный старый документ. Исходное
поручение отменить и создать замену разрешает оба шага без повторного согласия;
завершённость первого шага проверяется прежде, чем выполнять зависимый второй.

### Решения по текущему состоянию и восстановление

Названия в первом столбце описывают бизнес-состояние; они не заменяют
буквальные `status` и сообщения в возвращённом черновике.

| Наблюдаемое состояние | Доступное действие | Что проверять перед следующим шагом |
| --- | --- | --- |
| Только локальная подготовка, POST не отправлялся | Читать, уточнить условия и подготовить другой вариант. Поставщицкая отмена не нужна. | Наличие `submitted_at` и сохранённых этапов, а не слово «заявка» в разговоре. |
| Спецификация создана и найдена; резервирование не отправлялось | Читать, отменить `D`, изменить `C`, подтвердить `A` или оформить `invoice_order` согласно поручению. | Точные ID, номер клиента, контрагент, состав, сумма и живое состояние. Это известный объект, а не неизвестный исход создания. |
| Создание вернуло несколько документов | Выполнить порученное действие для всего подтверждённого набора. | Все исходные и итоговые ID; отсутствие пропущенных товарных строк и сумм. |
| Заказ принят, резерв или доставка подтверждены | Читать, печатать документы, выполнять разрешённые действия для текущего этапа. | Живые `operations`, оплаты и доставку; не применять правила свободной спецификации к начавшейся отгрузке. |
| Отправка оборвалась, результат конкретного POST неизвестен | Вызвать `status` прежнего черновика и читать точные документы; независимые чтения и подготовки продолжают работать. | Сохранённый ответ, известные ID и номер, все страницы поиска. Слепой повтор того же POST не допускается. |
| Отмена принята, но её результат ещё не подтверждён | Повторять чтение прежней операции. | Подтверждённое конечное состояние целевых документов. HTTP 200 или пустая поисковая страница недостаточны. |
| Отмена подтверждена | Завершить связанный прежний workflow и выполнить уже порученную замену. | Сохранённая связь между отменой и прежними документами; история и receipts не удаляются. |
| Замена `C` подтверждена | Продолжать с новыми ID, сохраняя связь с прежними. | Состав, условия и состояние всех новых документов, завершённость прежних. |

Чтение, расчёт, подготовка, получение PDF и сверка не блокируются чужой
незавершённой закупкой. Запись проверяет конфликт с тем же документом или
намерением. Блокировка на время одновременной работы сохраняет порядок
операций; она не превращается в бессрочный запрет на всю учётку.
Неизвестный результат не исправляется удалением JSON черновика, ручным
присвоением успешного статуса или новым заказом с другим номером.

Прямой `invoice_order` сверяет статус и точный `st_dest` каждого возвращённого
документа, а также переданное примечание `tovzak`. Это не заменяет проверки
количеств, договора и физического распределения полного `order_checkout`.
Если ответ потерян или не содержит ID, читается исходный документ из `path.id`;
другие документы с тем же номером сохраняют неопределённость возможного
разделения, пока их связь и итог не подтверждены. Для `invoice_delivery`
опубликованная схема чтения даёт `delivery`, `delivery_status`, `delivery_name`,
но не подтверждает точные `adr`, дату, временное окно и телефон запроса.
Один ID доставки поэтому не переводит операцию в подтверждённо выполненную.
Для комментария проверяется полный текст; для согласования — текущее значение
`agreed`. Неописанные в схеме признаки итогового `docStatus`, ожидания `sg=3`
и внутренней видимости сообщения сохраняются как неподтверждённые условия.

При чтении документа следует различать поля:

- `id` / `invnetnum` — идентичность документа, `usr_inv_num` / `invnum` —
  его видимый номер; точные связи проверяются по исходному ответу.
- `status_code`, `status_name`, `invStatus` — состояние, а `operations.cancel`,
  `edit`, `reserve`, `del_reserve`, `delivery`, `hist` — допустимые действия.
- `st_code` и body `store` — текущий склад; `st_dest` — склад-получатель.
- `pay` и body `paysum` — сумма оплат; `pay_sum` — остаток к оплате.
- `delivery`, `delivery_status`, `delivery_name` — сведения о доставке;
  отсутствие резерва или оплаты не выводится только из нулевого остатка к оплате.
- `cli_code`, сведения покупателя, все товарные строки и общая сумма —
  проверка нужного юрлица и состава; `/ps` — проверка сообщений и согласований.

Если ЭТМ возвращает новый ID вместо прежнего по автоматически созданному
UUID-номеру клиента, отмена может включить оба ID после сверки: исходная
квитанция полная, резерв не отправлялся, контрагент и количества совпадают,
оба документа — неоплаченные спецификации либо уже отменены. Старый ID
не подменяется новым и не объявляется отменённым заранее. Завершение требует
подтверждения отмены обоих; чтение исходного checkout учитывает найденные
документы с тем же номером. Для произвольных номеров, иных товаров, оплаты,
резерва и неизвестных семейств автоматическое расширение цели не применяется.
